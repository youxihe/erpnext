# POC-06 — 负面测试、中文使用体验、交接

## 目标
不仅能“跑通幸福路径”，还要知道库存、权限、中文、复杂度能否实际用于客户。最后给用户一个保持运行的登录地址与用例编号。

## 必测
1. 第二张生产销售订单也需要同一原材料时，检查 BOM 需求、可用库存、有效预留与在途采购防止重复分配；如果原生设置下无法明确预留，标 GAP，不自行开发复杂 MRP。
2. 对耗材和零部件直接出库分别验证数量不能超卖（遵守原生库存设置），并证明不会产生 Work Order。服务类完成履约时仓库数量绝不变化。
3. 车间账户不应访问财务敏感数据；销售员工不能修改库存单据。至少用直达 URL 验证一次服务端权限，不是只隐藏菜单。
4. 普通新建用户默认汉语，桌面菜单切换无白页、重复多标签页、404；抽查 10 个高频术语和按钮。
5. Docker/Bench 重启验证 URL、语言、菜单、4 张订单、库存台账仍然存在；提供备份和恢复实测证据（恢复可对隔离副本验证，严禁覆盖唯一 POC）。
6. 汇总 ERPNext 与 JSH ERP 对比：客户报备、按订单设计 BOM、轻任务粒度、统一采购缺口、物料成本、交付和财务简化，哪些可以原生复用，哪些需要配置或自研；说明最容易产生复杂度的 5 个页面。
7. 必须输出一页给用户的验收指南：准确的 Windows 浏览器地址、登录方法、演示角色、四类订单实际单号、生产订单链路访问位置和关键功能如何点击。密码通过本地安全交接，不得写入 GitHub。
8. 完成后**不要擅自迁移 JSH 数据，也不要马上投入正式产品开发**。等待用户自行体验和给出取舍。

## DoD
- docs/poc/UAT.md 每项 PASS/FAIL/BLOCKED 诚实记录，链接到单据与证据。
- 交付运行命令、版本、端口、配置恢复、样本单号、中文截图。
- 推荐选型（继续 JSH / ERPNext / 再验证）应建立在真实 POC 而非“ERPNext 功能多”上。
